### 짐벌락 처리 및 쿼터니안 사용
- **문제 정의**: 유니티 오일러 오브젝트 회전의 짐벌락 문제 고려
- **테스트 내용**:
- 유니티 월드 좌표축을 기준으로 세 비행기 오브젝트를 준비.
	1. x축 회전이 0인 기준 오브젝트
	2. x축 회전이 -90도이며 오일러 회전이 적용된 짐벌락 오브젝트
	3. x축 회전이 같은 -90도이며 쿼터니안 회전을 적용한 오브젝트
	단, x축은 Pitch, y축은 Yaw, z축은 Roll 회전으로 정의
	![비행기 축 정의](https://github.com/user-attachments/assets/8c80f4c5-3b58-4daa-9c51-04af58d27d76)
	<sub>[출처] Wikiversity</sub>

- Z축(Roll) 회전 테스트
![Z축 회전 테스트](https://github.com/user-attachments/assets/d01b4763-b6ae-4887-bf69-649018fb790e)
> Z축 회전 시에는 오일러 각과 쿼터니언 모두 의도한 대로 문제없이 회전함. (Roll)

- Y축(Yaw) 회전 테스트
![Y축 회전 테스트](https://github.com/user-attachments/assets/5dd42592-a9a3-4a98-a865-968ffad413c3)
> 오일러 회전: 짐벌 락으로 인해 Y축(Yaw) 회전이 Z축(Roll) 회전처럼 인식, 작동해 의도하지 않은 축 방향 회전 발생.  
> 쿼터니언 회전: 의도대로 잘 회전함. (Yaw)

- **핵심 성과**:
- 유니티 엔진 내에선 오일러 회전 시, Z축 -> X축 -> Y축 순서로 회전시키는 점을 알아냄.
- 상위 구조 순서로 부모 Y축, 자식 X축, 자손 Z축 계층구조로 되어있음. Z축 회전시 독립적으로, X축 회전시 Z축도 함께, Y축 회전시 모든 축이 함께 회전함. (짐벌 구조)
- 오일러 회전 테스트 시, X축 -90도 회전으로 인해 Z축이 함께 회전하여 움직이지 않던 Y축과 축이 겹쳐버려 자유도(Degree of Freedom)를 상실함. 같은 회전으로 인식하는 문제 발생.  
![짐벌락](https://github.com/user-attachments/assets/03aed650-3e8e-404e-8b21-4145b8e797a4)  
<sub>[출처] 구글 이미지 검색</sub>
- 오일러 회전은 변수 간의 종속성(coupling)이 발생하여 독립적인 제어력을 상실할 수 있음. (R = Rz Ry Rx)

- 쿼터니안 회전은 3개의 독립된 x, y, z축을 순서대로 회전시키는 대신, 4차원 공간의 하나의 회전축 w을 기준으로 물체를 한 번에 회전시키기 때문에 짐벌락이 일어나지 않음.
- 쿼터니안 회전은 복소 사원수 w + xi + yj + zk를 이용해 4차원으로 확장하여 한번에 이동함. 순차적인 축 회전이라는 개념이 없으므로 짐벌락이 일어나지 않음.
- 유니티 내 쿼터니안은 메서드 오버로딩 "*"를 사용하여 "오브젝트의 기존 위치 정보 * 원하는 회전 방향 쿼터니언"을 사용하여 오브젝트의 로컬 축을 중심으로 회전한다는 사실을 알아냄.
- 반대로, "쿼터니언 * 오브젝트의 기존 위치 정보" 순서로 연산할 시, 월드 좌표계에서 계산된 쿼터니안이 기준이 되므로 오브젝트가 월드좌표를 기준으로 회전함.
- 실제 수학 쿼터니안 계산 공식과 순서가 반대임을 깨달음. (수식 p나중 = q * p처음 * q-1)
- 결론: 해당 프로젝트에서 아두이노 센서 데이터를 받아 오일러 회전 각을 쿼터니안으로 변환, 저장하는 Quaternion.Euler(Vector3)을 적극 사용할 예정.
- 데이터 사용 과정에서 오브젝트 제어의 오염과 짐벌락을 막을 예정.

### 아두이노 데이터 패킷 구조 수정
- **기존**: String을 사용한 문자열로 ","를 통해 데이터 타입을 구분함.
- **문제점**: Update 내에서 Split(",")을 호출함으로서 힙(Heap) 영역에 가비지를 생성하여 가비지 컬렉터(GC) 및 성능 저하 문제를 고려함.  
Split을 사용 시, 기존 String 데이터 토큰을 쪼개 같은 주소에 다시 저장하는 것이 아닌 복사본을 데이터 개수에 따라 여러개 생성한다는 것을 알게됨.  
따라서, 프레임 드랍 등 성능 저하 문제를 예상함.
- **해결**: 데이터 패킷 구조를 ","이 포함된 String 대신 1 Byte 단위로 보내고 유니티 내에서 규격에 맞게 해석하여 더 빠르게 처리하고 가비지 생성 문제를 방지함.  
더해서, 기존에 없던 헤더 2바이트와 트레일러 2바이트를 정의하여 실제 네트워크처럼 헤더 총 4바이트를 검사하고 데이터가 올바른지 판단하는 구조를 넣음.
또한, 헤더 2바이트 아래에 데이터 패킷의 크기를 보내 유니티에서 1 패킷 당 데이터의 종류 개수를 파악하여 1패킷 단위를 감지할 수 있도록 함.

### 상보필터 구현 및 도입
- **문제 정의**: 비행기 오브젝트 회전에 자이로 센서 데이터를 사용시 센서 회전에 따라 오브젝트 회전이 잘 대응됨.
허나, 시간이 경과함에 따라 데이터가 한쪽으로 쏠리는 드리프트(Drift) 현상이 생길 것임을 파악함.
자이로 데이터는 각속도(Degree/sec) 타입이기 때문에 프레임 간격 시간으로 적분하여 누적하여 각도를 구해야함. 이때 런타임 시간 경과마다 누적오차가 한쪽으로 오브젝트가 의도하지 않게 쏠리는 드리프트 현상이 일어남을 알아냄.
만약, 비행기 오브젝트 회전에 가속도 센서 데이터를 이용할 시 회전 대응이 잘 일어나고 드리프트 현상도 일어나지 않는 장점이 있었음.
허나, 센서 회전 시 오브젝트가 심하게 흔들리고 센서 회전 반응에 굉장히 민감하다는 사실을 알아냄.
각각의 단점을 보완하기 위해 두 센서 데이터의 가중치를 두고 계산하여 오브젝트를 제어하는 "상보필터"를 도입함.

- **구현 방법** (FlightRotationController.cs 참조):
1. 현실 센서 축과 유니티 월드 축의 방향과 축을 매핑하고(자이로, 가속도) 회전 방향 기준 차이에 따른 음수처리를 진행함 (자이로).
2. 매핑한 자이로 각속도 데이터를 이용해 프레임 간격 별 미소 쿼터니안 누적 회전을 계산함. 이를 통해 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 구함.
3. 매핑한 가속도 데이터를 이용해 정규화(Normalized) 벡터를 구한다.
4. 가속도 정규화 벡터에 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 적용하여, 자이로 센서로 예측한 좌표계의 하늘 방향 (중력 가속도의 반대 방향) 벡터를 계산한다.
5. 실제 중력에 반대인 하늘 방향(Vector3.up)과의 오차 회전 구한다. MPU 센서 원리 상 가속도가 적용되는 반대의 방향으로 가속도 센서의 값이 출력되기 때문에 중력 방향(Vector.down)이 아닌 하늘방향과 비교한다.
6. 쿼터니안 Lerp 메서드를 통해 5번의 오차 회전 쿼터니안에 가속도 가중치 비율(ex. 4%)만큼 구한다.
7. 2번의 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 사용하기 전, 쿼터니안 곱을 통해 해당 쿼터니언과 6번의 가속도 가중치 적용 쿼터니언(4%)을 곱해 최종 회전 쿼터니안을 구한다.  
쿼터니안 곱 특성 상 자이로 예측 회전 쿼터니언이 가속도 쿼터니언의 (4%)만큼 상쇄되므로, 자이로 가중치(ex. 96%) = 1 - 가속도 가중치(4%) 만큼 적용 될 것이다.
8. 오브젝트 회전값에 7번 최종 회전 쿼터니안을 적용한다. (상보필터 적용 완료)

> 자이로 쿼터니안 회전의 가중치를 직접 설정할 수 있도록 직렬화함.

- **테스트 내용**:   
상보필터의 신뢰도를 검증하기 위해 가중치 테스트를 진행함.  
자이로 가중치 + 가속도 가중치 = 1 인 조건 하에, 자이로 가중치를 각각 "1, 0.96, 0.5, 0"씩 적용하고 회전 테스트를 진행함.

- 실시간 런타임 회전 테스트

> 런타임 드리프트 테스트 (40분, 32배속)  

자이로 가중치가 1인 비행기 오브젝트만 시간이 경과함에 따라 미세하게 한쪽으로 쏠리는 드리프트 현상이 생김.
반면, 가속도 가중치가 크거나 조금이라도 적용된 오브젝트는 드리프트 현상이 일어나지 않음.
첫 런타임 초기에는 이상이 없어 보이지만, 시간이 누적됨에 따라 오브젝트가 한쪽으로 쏠리는 오차 현상이 발생함.
> (테스트 내 Yaw, Y축 데이터를 0으로 적용한 이유는 아래 트러블 슈팅의 "하드웨어(MPU6050) 제약에 따른 수평축(Yaw) 드리프트 한계" 참조)

- **핵심 성과**:  
- 상보필터 구현:  
MPU6050 센서 자체 라이브러리를 통해 쿼터니안 및 상보필터를 아두이노 측에서 직접 계산할 수 있음.
그러나 상보필터 원리 파악 및 유니티의 더 많은 계산 자원 사용, 아두이노 부하 방지를 같은 성능 향상을 고려해 유니티 스크립트 내 구현함.

- 런타임 테스트:  
"실시간 런타임 회전 테스트"를 통해 가속도 보정 비율을 높게 두었을 때는 노이즈나 기준 오차가 즉각 반영되어 제어 대상이 급격히 요동침을 알아냄.
반면, "40분 런타임 드리프트 테스트"를 통해서 자이로 보정만을 사용했을 때는 오차가 매 프레임 누적되면서 아주 느린 속도로 서서히 잘못된 자세로 수렴하는 것을 확인함.
두 테스트를 통해 가속도/자이로 센서 간 상호 보완의 정밀한 튜닝이 필수적임을 검증함. 저주파 특성인 자이로 데이터와 고수파 특성인 가속도 데이터를 상보 결합하는 것이 중요함을 알아냄.
이를 통해 쿼터니안 회전 시스템이 안정적이면서도 빠르게 오차를 보완할 수 있는 최적의 자이로 가중치 상수가 0.96 내외임을 체득함.
해당 프로젝트 내에서 자이고 가중치를 0.96 정도로 사용하고자 결정함.

### 엔진 관성 및 미끄러짐 조정 기능
- **문제 상황**:
- 비행기 로컬 축 기준 전방으로 가속되는 상황에서 방향 회전 시, Rigid Body 물리 엔진의 관성 현상이 나타남.
방향 회전 이전 가속 방향이 남아있는 관성 현상 때문에 원하는 방향으로의 가속 전진이 무겁게 느껴지는 현상이 일어남.

- **해결 방법**:
1. 비행기 오브젝트의 현재 전방 방향의 속도 벡터를 구한다: Aligned Velocity 벡터
> transform.forward 와 flightRigidbody.linearVelocity.magnitude 스칼라 적용 벡터
2. 매 프레임마다 관성이 적용된 비행기 오브젝트의 현재 속도 벡터에 Aligned Velocity의 보간 (Lerp)을 적용해 속도 벡터를 보정한다.
3. 보간 비율을 velocityAlignmentRate로 조정하여 원하는 조정 강도를 설정할 수 있다.

- **테스트 내용**:
기울기 센서를 아래 수직 방향으로 꺾어 비행기 오브젝트의 관성 적용 여부를 테스트한다.

- **핵심 성과**
물리 연산의 조종감을 가변 제어할 수 있게됨.
아두이노 센서로 오브젝트의 몸통(Rotation)만 돌고 진행 방향(Velocity)이 따라오지 않아 붕 떠 밀리던 현상을 보완할 수 있게됨.
아두이노 센서 회전 로직은 100% 온전히 유지하면서, 속도 정렬 비율(velocityAlignmentRate) 값 하나만으로 방향 전환이 무거운 우주선, 여객기 부터 상대적으로 가벼운 전투기 까지 다양한 조종감을 설정할 수 있도록 구축함.
본 프로젝트에서는 가벼운 회전 제어를 사용하기 위해 비율을 비교적 높게 설정 할 예정임.

## 트러블 슈팅
### 바이트 스트림 데이터 패킷과 Concurrent Queue 호환 문제
- **기존**: SerialManager.cs 내 기존 사용하던 멀티 스레드 용 Concurrent Queue를 사용하는 환경에서, 데이터 패킷을 String 대신 바이트 스트림 단위로 데이터 패킷 타입을 변경함.
- **문제점**: 복사본 배열 checkArray을 만들어 패킷의 구조를 확인하기 위해 ToArray나 CopyTo 메서드를 사용할 때 디버깅 시 에러가 발생함.
에러가 발생한 원인은 Update() 메서드 안에서 dataQueue.CopyTo(checkArray, 0)을 호출할 때, dataQueue에 쌓여있는 데이터 개수가 멤버로 캐싱 (미리 선언)한 checkArray의 크기(256)보다 커졌기 때문이었음.
이 방법을 채택한 이유로, ConcurrentQueue는 인덱스로 따로 접근할 수 없는 자료구조의 자체 보안성 문제가 있어 배열 복사본 생성을 선택했음.
그러나, 데이터가 쌓이는 속도가 너무 빨라서 어느 순간 dataQueue.Count가 256 Byte을 넘어가버려서 고정 크기인 checkArray에 통째로 복사하려다 보니 공간이 부족해서 ArgumentException이 발생함.
또한, ToArray도 마찬가지로 같은 에러가 뜸과 동시에 Heap 영역에서 생성하므로 가비지 컬렉터를 일으킬 여지가 있었음.
단순히 복사본 배열 바이트 크기 선언을 늘리는 방법도 추후 해당 데이터 수용 스크립트의 유지 보수 문제가 생길 것이라고 판단함.
- **해결**: 다시 처음 lock 오브젝트 방식을 채택하되, 기존과 다르게 lock 오브젝트와 일반 Queue를 같이 사용함.
lock 오브젝트 제어를 통해 멀티 스레드 환경 내 큐의 데이터 보호 수준 안전을 보장함과 동시에, ConcurrentQueue의 인덱스 접근 불가 문제를 일반 Queue로 사용해서 데이터 패킷을 바이트 단위 인덱스로 접근해 두 장점을 모두 살릴 수 있는 방법을 선택함.
또한, Enumerator 열겨형을 채택하여 큐내 바이트 데이터 요소(Element)를 가르키는 이정표 기능으로 이용해 직접 내부로 참조만 하도록 설계함.
이 방식으로 큐 배열을 굳이 복사하지 않고도 헤더와 사이즈, 트레일러를 안전하게 확인하며 동시에 가비지 컬렉터 문제도 방지하는 좋은 방법이 됨.
이 방식을 사용해서 바이트 단위로 데이터를 받아 String과 Split(",") 방식을 사용한 기존보다 유니티에서 더 빠르게 처리할 수 있게 되었음.
또한 큐 방식을 그대로 사용하여 데이터 유실을 방지도 함께 챙길 수 있게 됨.
(데이터 바이트 패킷 -> int 조립 방식은 BitConverter를 사용함; PC환경에 맞춰 리틀 엔디안(Low -> High)으로 자동 조립(window))

lock 오브젝트 사용 성능 검증
1. Serial 버퍼로 부터 바이트 단위 데이터를 읽어올 때 (Enqueue일 때만 lock 시스템 이용)
2. while문 내 일반 Queue 인덱스를 확인할 때 (Dequeue일 때만 lock 시스템 이용)

* 1번의 경우보다 2번의 while문 처리 속도가 시스템 상 훨씬 빠름. 센서 데이터를 받아오는 속도보다 유니티에서 while로 읽고 Dequeue 처리하는 속도가 훨씬 빨라 데이터 유실이 일어나지 않는다.
시리얼 통신이나 네트워크 환경에서 데이터를 읽어올 때, ReadByte()를 단발성으로 호출하는 방식과 while문을 돌며 버퍼를 통째로 비우는 방식의 속도 차이는 매우 크다.
CPU가 while 루프를 돌며 메모리에서 데이터를 Dequeue하는 속도는 나노 초에서 마이크로 초 단위이며, ReadByte()는 상대적으로 매우 느리게 센서 데이터를 Enqueue하므로 최소 100배에서 1,000배 이상 차이가 남.
즉, 데이터 패킷 유실이 일어나지 않는 구조를 가질 수 있음.

* 멀티 스레드 환경 내 lock 오브젝트를 사용하여도, 1번과 2번의 Enqueue와 Dequeue 내에서만 lock 제어를 사용하므로 프로그램의 성능에 거의 영향을 주지 않는다.
큐(Queue) 자료구조에서 데이터를 넣고(Enqueue) 빼는(Dequeue) 작업의 시간 복잡도는 모두 O(1) (상수 시간)이기 때문이다.

### 하드웨어(MPU6050) 제약에 따른 수평축(Yaw) 드리프트 한계
- **물리적 한계 파악**: 본 프로젝트에 사용된 MPU6050 센서는 6축(가속도 3축, 자이로 3축) 기반으로 지구 자기장을 측정할 수 있는 지자기 센서(Magnetometer)가 누락되어 있다.
MPU6050 센서를 이용한 상보 필터 적용으로 Roll과 Pitch의 기울기는 실시간 세계 기준(중력 방향)으로 완벽히 보정했으나, 수평 방위각(Yaw)은 가속도 기준점을 측정할 수 없었다.
측정할 수 없는 이유는 Yaw 방위각(수평면에서의 회전)으로 어떻게 회전하든 중력 가속도는 항상 수직 아래로 작용하므로, Yaw 회전만으로는 센서의 중력 가속도의 크기나 방향이 변하지 않기 때문임.
이는 수평 방위각(Yaw) 계산할 정보 자체가 가속도계에 없기 때문에 오직 자이로 데이터만을 사용할 수 밖에 없었음. 이로 인해 Yaw는 누적 오차(Drift)가 발생할 수밖에 없는 하드웨어적 한계가 존재함.

> 수평 방위각 Yaw 드리프트 테스트 (17분, 32배속)

센서를 가만히 놔두고 17분간 런타임을 진행하였음. 상보필터가 얼마가 적용되던 네 오브젝트 모두 특정 방향으로 쏠리는 오차 누적 현상이 발생함.
가속도 가중치가 1이어도, 쿼터니안 곱 특성 상 자이로 예상 회전 쿼터니언에 가속도 Yaw 보정값만이 관여할 수가 없기 때문에 자이로 드리프트(Drift)를 피할 수 없음.

- **추후 개선 사항**: 채택한 MPU6050 센서가 지자기 센서가 빠진 보급형 센서라는 점, Yaw 드리프트를 잡을 수 없다는 물리적 한계점을 개발 중 늦게 알아냄.
그러하여 소프트웨어적으로 억지로 방위각을 왜곡하여 데이터 무결성을 해치는 대신, 하드웨어의 특성을 그대로 수용함.
차기 버전에서는 지자기 센서가 함께 있는 MPU9250나 BNO055 9축 IMU 센서를 도입해, 자기장 데이터를 기반으로 한 Yaw 축 보정을 보완할 계획임.

## 데이터 패킷 구조 정의
- 아두이노에서 유니티로 전송되는 바이너리 패킷 구조.

| 바이트 위치 (Index) | 데이터 항목 (Data Item) | 데이터 타입 / 설명 (Type & Description) |
| :--- | :--- | :--- |
| **0 ~ 1** | **Packet Header** | `0xAA`, `0xBB` (패킷 시작 알림) |
| **2** | **Packet Size (Byte)** | `int8_t` (센서 데이터 총 크기 (Byte)) |
| **3 ~ 4** | Accel X | `int16_t` (MPU6050 가속도 X축 Raw Data) |
| **5 ~ 6** | Accel Y | `int16_t` (MPU6050 가속도 Y축 Raw Data) |
| **7 ~ 8** | Accel Z | `int16_t` (MPU6050 가속도 Z축 Raw Data) |
| **9 ~ 10** | Gyro X | `int16_t` (MPU6050 자이로 X축 Raw Data) |
| **11 ~ 12** | Gyro Y | `int16_t` (MPU6050 자이로 Y축 Raw Data) |
| **13 ~ 14** | Gyro Z | `int16_t` (MPU6050 자이로 Z축 Raw Data) |
| **15 ~ 16** | Button Click Signal | `int16_t` (버튼 클릭 시 `1`, 평상시 `0`) |
| **17 ~ 18** | **Packet Tailer** | `0xCC`, `0xDD` (패킷 끝 알림) |
