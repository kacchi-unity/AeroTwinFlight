	단, x축은 Pitch, y축은 Yaw, z축은 Roll 회전으로 정의

- Y축(Yaw) 회전 테스트
![Y축 회전 테스트](https://github.com/user-attachments/assets/5dd42592-a9a3-4a98-a865-968ffad413c3)
> 오일러 회전: 짐벌 락으로 인해 Y축(Yaw) 회전이 Z축(Roll) 회전처럼 인식, 작동해 의도하지 않은 축 방향 회전 발생.  
> 쿼터니언 회전: 의도대로 잘 회전함. (Yaw)

- **핵심 성과**:
- 유니티 엔진 내에선 오일러 회전 시, Z축 -> X축 -> Y축 순서로 회전시키는 점을 알아냄.
- 상위 구조 순서로 부모 Y축, 자식 X축, 자손 Z축 계층구조로 되어있음. Z축 회전시 독립적으로, X축 회전시 Z축도 함께, Y축 회전시 모든 축이 함께 회전함. (짐벌 구조)
- 오일러 회전 테스트 시, X축 -90도 회전으로 인해 Z축이 함께 회전하여 움직이지 않던 Y축과 축이 겹쳐버려 자유도(Degree of Freedom)를 상실함. 같은 회전으로 인식하는 문제 발생.  
![짐벌락](https://github.com/user-attachments/assets/03aed650-3e8e-404e-8b21-4145b8e797a4)  
<sub>[출처] 구글 이미지 검색</sub>
- 오일러 회전은 변수 간의 종속성(coupling)이 발생하여 독립적인 제어력을 상실할 수 있음. (R = Rz Ry Rx)

- 쿼터니안 회전은 3개의 독립된 x, y, z축을 순서대로 회전시키는 대신, 4차원 공간의 하나의 회전축 w을 기준으로 물체를 한 번에 회전시키기 때문에 짐벌락이 일어나지 않음.
- 쿼터니안 회전은 복소 사원수 w + xi + yj + zk를 이용해 4차원으로 확장하여 한번에 이동함. 순차적인 축 회전이라는 개념이 없으므로 짐벌락이 일어나지 않음.
- 유니티 내 쿼터니안은 메서드 오버로딩 "*"를 사용하여 "오브젝트의 기존 위치 정보 * 원하는 회전 방향 쿼터니언"을 사용하여 오브젝트의 로컬 축을 중심으로 회전한다는 사실을 알아냄.
- 반대로, "쿼터니언 * 오브젝트의 기존 위치 정보" 순서로 연산할 시, 월드 좌표계에서 계산된 쿼터니안이 기준이 되므로 오브젝트가 월드좌표를 기준으로 회전함.
- 실제 수학 쿼터니안 계산 공식과 순서가 반대임을 깨달음. (수식 p나중 = q * p처음 * q-1)
- 결론: 해당 프로젝트에서 아두이노 센서 데이터를 받아 오일러 회전 각을 쿼터니안으로 변환, 저장하는 Quaternion.Euler(Vector3)을 적극 사용할 예정.
- 데이터 사용 과정에서 오브젝트 제어의 오염과 짐벌락을 막을 예정.

### 아두이노 데이터 패킷 구조 수정
- **기존**: String을 사용한 문자열로 ","를 통해 데이터 타입을 구분함.
- **문제점**: Update 내에서 Split(",")을 호출함으로서 힙(Heap) 영역에 가비지를 생성하여 가비지 컬렉터(GC) 및 성능 저하 문제를 고려함.  
Split을 사용 시, 기존 String 데이터 토큰을 쪼개 같은 주소에 다시 저장하는 것이 아닌 복사본을 데이터 개수에 따라 여러개 생성한다는 것을 알게됨.  
따라서, 프레임 드랍 등 성능 저하 문제를 예상함.
- **해결**: 데이터 패킷 구조를 ","이 포함된 String 대신 1 Byte 단위로 보내고 유니티 내에서 규격에 맞게 해석하여 더 빠르게 처리하고 가비지 생성 문제를 방지함.  
더해서, 기존에 없던 헤더 2바이트와 트레일러 2바이트를 정의하여 실제 네트워크처럼 헤더 총 4바이트를 검사하고 데이터가 올바른지 판단하는 구조를 넣음.
또한, 헤더 2바이트 아래에 데이터 패킷의 크기를 보내 유니티에서 1 패킷 당 데이터의 종류 개수를 파악하여 1패킷 단위를 감지할 수 있도록 함.

### 상보필터 구현 및 도입
- **문제 정의**: 비행기 오브젝트 회전에 자이로 센서 데이터를 사용시 센서 회전에 따라 오브젝트 회전이 잘 대응됨.
허나, 시간이 경과함에 따라 데이터가 한쪽으로 쏠리는 드리프트(Drift) 현상이 생길 것임을 파악함.
자이로 데이터는 각속도(Degree/sec) 타입이기 때문에 프레임 간격 시간으로 적분하여 누적하여 각도를 구해야함. 이때 런타임 시간 경과마다 누적오차가 한쪽으로 오브젝트가 의도하지 않게 쏠리는 드리프트 현상이 일어남을 알아냄.
만약, 비행기 오브젝트 회전에 가속도 센서 데이터를 이용할 시 회전 대응이 잘 일어나고 드리프트 현상도 일어나지 않는 장점이 있었음.
허나, 센서 회전 시 오브젝트가 심하게 흔들리고 센서 회전 반응에 굉장히 민감하다는 사실을 알아냄.
각각의 단점을 보완하기 위해 두 센서 데이터의 가중치를 두고 계산하여 오브젝트를 제어하는 "상보필터"를 도입함.

- **구현 방법** (FlightRotationController.cs 참조):
1. 현실 센서 축과 유니티 월드 축의 방향과 축을 매핑하고(자이로, 가속도) 회전 방향 기준 차이에 따른 음수처리를 진행함 (자이로).
2. 매핑한 자이로 각속도 데이터를 이용해 프레임 간격 별 미소 쿼터니안 누적 회전을 계산함. 이를 통해 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 구함.
3. 매핑한 가속도 데이터를 이용해 정규화(Normalized) 벡터를 구한다.
4. 가속도 정규화 벡터에 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 적용하여, 자이로 센서로 예측한 좌표계의 하늘 방향 (중력 가속도의 반대 방향) 벡터를 계산한다.
5. 실제 중력에 반대인 하늘 방향(Vector3.up)과의 오차 회전 구한다. MPU 센서 원리 상 가속도가 적용되는 반대의 방향으로 가속도 센서의 값이 출력되기 때문에 중력 방향(Vector.down)이 아닌 하늘방향과 비교한다.
6. 쿼터니안 Lerp 메서드를 통해 5번의 오차 회전 쿼터니안에 가속도 가중치 비율(ex. 4%)만큼 구한다.
7. 2번의 자이로 데이터만으로 예측한 현재 프레임의 회전 쿼터니안을 사용하기 전, 쿼터니안 곱을 통해 해당 쿼터니언과 6번의 가속도 가중치 적용 쿼터니언(4%)을 곱해 최종 회전 쿼터니안을 구한다.  
쿼터니안 곱 특성 상 자이로 예측 회전 쿼터니언이 가속도 쿼터니언의 (4%)만큼 상쇄되므로, 자이로 가중치(ex. 96%) = 1 - 가속도 가중치(4%) 만큼 적용 될 것이다.
8. 오브젝트 회전값에 7번 최종 회전 쿼터니안을 적용한다. (상보필터 적용 완료)

> 자이로 쿼터니안 회전의 가중치를 직접 설정할 수 있도록 직렬화함.

- **테스트 내용**:   
상보필터의 신뢰도를 검증하기 위해 가중치 테스트를 진행함.  
자이로 가중치 + 가속도 가중치 = 1 인 조건 하에, 자이로 가중치를 각각 "1, 0.96, 0.5, 0"씩 적용하고 회전 테스트를 진행함.

- 실시간 런타임 회전 테스트  
센서를 직접 좌우, 상하, 양옆으로 움직이며 오브젝트 떨림의 정도의 비교를 진행함.

자이로 가중치가 1인 비행기 오브젝트만 시간이 경과함에 따라 미세하게 한쪽으로 쏠리는 드리프트 현상이 생김.
반면, 가속도 가중치가 크거나 조금이라도 적용된 오브젝트는 드리프트 현상이 일어나지 않음.
첫 런타임 초기에는 이상이 없어 보이지만, 시간이 누적됨에 따라 오브젝트가 한쪽으로 쏠리는 오차 현상이 발생함.
> (테스트 내 Yaw, Y축 데이터를 0으로 적용한 이유는 아래 트러블 슈팅의 "하드웨어(MPU6050) 제약에 따른 수평축(Yaw) 드리프트 한계" 참조)

- **핵심 성과**:  
- 상보필터 구현:  
MPU6050 센서 자체 라이브러리를 통해 쿼터니안 및 상보필터를 아두이노 측에서 직접 계산할 수 있음.
그러나 상보필터 원리 파악 및 유니티의 더 많은 계산 자원 사용, 아두이노 부하 방지를 같은 성능 향상을 고려해 유니티 스크립트 내 구현함.

- 런타임 테스트:  
"실시간 런타임 회전 테스트"를 통해 가속도 보정 비율을 높게 두었을 때는 노이즈나 기준 오차가 즉각 반영되어 제어 대상이 급격히 요동침을 알아냄.
반면, "40분 런타임 드리프트 테스트"를 통해서 자이로 보정만을 사용했을 때는 오차가 매 프레임 누적되면서 아주 느린 속도로 서서히 잘못된 자세로 수렴하는 것을 확인함.
두 테스트를 통해 가속도/자이로 센서 간 상호 보완의 정밀한 튜닝이 필수적임을 검증함. 저주파 특성인 자이로 데이터와 고수파 특성인 가속도 데이터를 상보 결합하는 것이 중요함을 알아냄.
이를 통해 쿼터니안 회전 시스템이 안정적이면서도 빠르게 오차를 보완할 수 있는 최적의 자이로 가중치 상수가 0.96 내외임을 체득함.
해당 프로젝트 내에서 자이고 가중치를 0.96 정도로 사용하고자 결정함.

### 엔진 관성 및 미끄러짐 조정 기능
- **문제 상황**:  
비행기 로컬 축 기준 전방으로 가속되는 상황에서 방향 회전 시, Rigid Body 물리 엔진의 관성 현상이 나타남.
방향 회전 이전 가속 방향이 남아있는 관성 현상 때문에 원하는 방향으로의 가속 전진이 무겁게 느껴지는 현상이 일어남.

- **해결 방법**:
1. 비행기 오브젝트의 현재 전방 방향의 속도 벡터를 구한다: Aligned Velocity 벡터
> transform.forward 와 flightRigidbody.linearVelocity.magnitude 스칼라 적용 벡터
2. 매 프레임마다 관성이 적용된 비행기 오브젝트의 현재 속도 벡터에 Aligned Velocity의 보간 (Lerp)을 적용해 속도 벡터를 보정한다.
3. 보간 비율을 velocityAlignmentRate로 조정하여 원하는 조정 강도를 설정할 수 있다.

- **테스트 내용**:  
기울기 센서를 아래 수직 방향으로 꺾어 비행기 오브젝트의 관성 적용 여부를 테스트한다.

![Alignment Test1](https://github.com/user-attachments/assets/c3202eea-4183-4a98-b763-eba3384e8415)

![Alignment Test2](https://github.com/user-attachments/assets/92bf0db7-c758-4100-b7c9-b70cff6327af)
> 단, 해당 계수는 velocityAlignmentRate

- **핵심 성과**  
물리 연산의 조종감을 가변 제어할 수 있게됨.
아두이노 센서로 오브젝트의 몸통(Rotation)만 돌고 진행 방향(Velocity)이 따라오지 않아 붕 떠 밀리던 현상을 보완할 수 있게됨.
아두이노 센서 회전 로직은 100% 온전히 유지하면서, 속도 정렬 비율(velocityAlignmentRate) 값 하나만으로 방향 전환이 무거운 우주선, 여객기 부터 상대적으로 가벼운 전투기 까지 다양한 조종감을 설정할 수 있도록 구축함.
본 프로젝트에서는 가벼운 회전 제어를 사용하기 위해 비율을 비교적 높게 설정 할 예정임.

### Attitude Control Mode 구현 (자세 제어 모드)
- **문제 정의**:  
기존 MPU6050 센서 회전을 비행기 오브젝트에 1:1로 매핑하는 절대적(Absolute) 미러 모드로 조종 테스트를 진행함.
그러나 비행기 오브젝트를 급선회시키거나 방향을 전환하기 위해 센서를 잡은 손목을 과도하게 꺾어야 하는 손목 뒤틀림 및 조작 피로도 문제가 발생함.
또한, 센서 방향을 원위치할 시 사용자의 의도대로 오브젝트 회전 방향을 고정할 수 없고 무조건 초기 센서 방향과 1:1로 일치하는 방향으로 다시 돌아오는 특성을 발견함.
(예: 실제 자동차 핸들처럼 방향을 돌려 몸체를 원하는 방향으로 바꾼 뒤 핸들 방향을 원위치 하여 회전 방향을 고정하기 등 -> 사용 불가)
또한 1:1 미러 모드에서는 단순 Yaw(제자리 회전) 축 조작으로 좌우 이동을 처리하여, 실제 항공기가 날개를 기울여(Roll) 대각선 양력과 중력의 영향으로 선회하는 실제 비행 메커니즘을 살리지 못함.

- **해결 방안**:  
1:1 미러 모드의 쿼터니언 회전 데이터를 재가공하여 조종 편의성과 비행감을 대폭 향상시킨 Attitude Control (AC) 모드를 도입함.

- **구현 방법** (AttitudeFlightRotationController.cs 참조):
1. 입력받은 절대 쿼터니언에서 월드 기준 z축 정면(forward), y축 상단(up), x축 우측(right) 방향 벡터를 수직 투영 연산하여 짐벌락 없는 Pitch 및 Roll 벡터를 추출함.
> 절대 쿼터니언은 상보필터를 적용해 이미 계산된 기존 FlightRotationController.cs 내 쿼터니안을 사용함.
2. Pitch 각도는 정면 벡터의 y 높이값 성분을 Asin으로, Roll각도는 우측 및 상단 벡터의 y 높이 비율을 Atan2로 계산하여 각도를 추출함.
3. 추출된 각도를 데드존(deadzoneAngle) 및 최대 센서 입력 각도(maxInputTiltAngle) 범위에 맞추어 -1.0 ~ 1.0 비율의 Power라는 데이터로 정제함.
> deadzoneAngle: 손떨림 방지 (0~4도), maxInputTiltAngle: 실제 센서 조작 손목 한계 기울기 및 최대 기울기 수용 각도 (약 45도)
4. 센서의 실제 물리적 Yaw 회전값은 사용하지 않고, 정제된 Roll 파워 비율에 비례하여 오브젝트 진행 방향 yaw 각도(currentYaw)를 누적 선회시킴.
5. pitch, roll 같은 경우, maxVisibleTurnAngle 값을 사전 정의해 시각적으로 Power 값 대비 오브젝트 회전 각도 계산 (약 75도로 설정함.)
6. 표준 3차원 축 합성 순서인 Yaw * Pitch * Roll 순서로 Quaternion.AngleAxis를 각각 만들어 곱연산함. 이를 통해 기체 회전축이 꼬이지 않는 단하나의 목표 쿼터니언(targetRotation)을 생성하고 회전에 적용함.

- **테스트 내용**  
기존 절대적 미러 모드(Absolute)와 자세 제어 모드 (Attitude Control)를 적용한 오브젝트의 제어를 테스트함.  
같은 MPU6050 센서를 사용하면서 각각 Yaw, Roll, Pitch 단일 회전을 순서대로 제어함.

| :--- | :--- | :--- |

| **센서 Pitch 회전시** | 센서 1:1 고도 회전 매핑 | 센서 Pitch 파워 비율 적용 고도 회전 |

- **핵심 성과**:
- 조작 반응성 및 뱅킹 연출
손목을 좌우로 기울였을 때 visual 한계 각도(maxVisibleTurnAngle)만큼 자연스럽게 오브젝트 선회 각을 지정하게됨.
손목을 좌우로 기울였을 때 기울임 지속 시간에 비례하여 Yaw 회전이 누적되어 쉬운 선회 시뮬레이션 가능.
또한 데드존을 사용해 손떨림 방지를 적용할 수 있었음. (deadzoneAngle)
손목 기울임 각도 한계를 고려하여 최대 yaw 회전 누적 각도를 얼마나 적용 크게 적용시킬건지 (yawTurnSpeed),
최댓 값을 출력할 수 있도록 하는 실제 센서 기울기 각도는 얼마나 할 것인지 인스펙터 설정 가능하도록 설계함 (maxInputTiltAngle).
손목을 과도하게 꺾지 않고도 센서 기울임만으로 원하는 방향까지 부드럽고 직관적인 뱅킹 선회가 가능해짐.

- 센서 Yaw 드리프트 차단 검증
Attitude Control 모드 연산식 내부에서 오직 벡터의 $Y$ 높이값 성분만 추려 쓰도록 설계함.
MPU6050 하드웨어 특성상 런타임 중 y축 제자리 회전 오차(Yaw Drift)가 누적되어 센서 좌표가 계속 돌아가더라도,
AC모드가 적용된 비행기 오브젝트에는 드리프트 오차가 필터링됨을 확인함. (보정 후 런터임 경과에 따른 y축 회전 값 관찰, 트러블 슈팅 참고)
AC 모드에서는 센서 쿼터니언에서 오직 월드 Y축(높이) 성분만을 추출하여 Pitch와 Roll을 연산함.
3차원 공간에서 수직 Y축을 중심축으로 한 제자리 회전(Yaw)은 대상 벡터의 x, y 좌표만 변화시킬 뿐, y값 성분에는 조금의 변화도 주지 않는 수학적 성질이 있기 때문.
따라서 AC모드의 연산 단계에서 yaw 드리프트는 수학적으로 필터링되어 실제 yaw값을 무시하고 Roll 기울임 Power로 가상 yaw를 생성 및 누적하므로 MPU6050의 고질적인 Yaw 드리프트 문제를 추가 센서 없이 해결가능한 모드임을 알아냄.

- AC모드의 한계: Mathf.Asin 기반 Pitch 연산의 한계 및 예외 처리
pitch를 추출 시 이용한 Asin은 치환 결과값 범위가 -90도 ~ 90도로 제한될 수 밖에 없어 절대 모드와 달리 AC모드에서는 90도 초과 회전 표현이 불가능함.
그렇기에 최대 입력 한계각(maxInputTiltAngle, 예: 45도)을 두어 Power로 매핑하므로 각도 제한이 실질적인 조작에 영향을 주지 않도록 함.

- 본 프로젝트는 Attitude Control 모드를 사용하며, 사용자 설정 기능으로 절대적 미러모드와 자세 제어 모드를 선택할 수 있도록 구현함.

### Cesium 및 구글 맵 API 3D Tiles 연동
- **도입 배경**:  
단순 지형(Terrain) 지구 전체를 3D로 시각화하고 정밀하게 분석할 수 있도록 도와주는 Cesium 플랫폼 연동에 더해,
실제 도시의 고밀도 3D 건축물 데이터를 연동하여 프로젝트의 사실성을 극대화하고자 Google Photorealistic 3D Tiles API를 도입함.  
Cesium 아키텍처를 통해 WGS84 위도·경도·고도 좌표를 연동하여, 원하는 도시 좌표를 선택할 수 있도록 오브젝트와 컴포넌트를 배치했고
향후 비행 오브젝트 도입 시 현실과 1:1 대응되는 위치 신뢰성을 확보하고자 함.

- **구현 방법 (Google API + Cesium)**  
유니티 내 패킷을 통해 Cesium 패키지를 Import함.
이후 Google Photorealistic 3D Tiles 오브젝트를 불러온 뒤, 구글 Map 3D Tile의 개인 API를 입력하여 구글 맵과의 연동을 성공함.
원하는 지역의 위도(Latitude)와 경도(Longitude), 고도(Height)를 입력할 시 구글 서버를 통해 지도 데이터를 가져와 실제 도시의 3D 텍스처를 불러올 수 있었음.

- **성능 최적화**  
- Maximum Screen Space Error기반 dynamic LOD 조절  
해당 패키지에서 지원하는 Tile Set은 거리와 화면 따라 LOD(Level of Detail)가 자동 계산되나, 기본값 적용 시 타일 요청 폭증으로 런타임 성능 저하 발생함.  
따라서, Maximum Screen Space Error 컴포넌트 값을 32~ 64 정도로 정밀 제어하여 화질 텍스처 디테일과 FPS 간의 균형을 테스트함. (작을수록 고화질 텍스터 사용)

> Maximum Screen Space Error(최대 화면 공간 오차)란: 3D 지형이나 타일 기반 그래픽스 시스템에서 디테일 수준(LOD, Level of Detail)을 결정하고 시각적 품질과 성능의 균형을 맞추는 렌더링 매개변수(설정 값)

- Cesium Cartographic Polygon 활용 영역 절삭 컴포넌트 사용  
카메라 시야 밖의 타일 렌더링을 줄이기 위해 맵의 영역을 잘라 해당 영역 지도 맵만 렌더링을 시키는 컴포넌트 도입.
좌표계 distortion(왜곡) 방지를 위해 Scale을 (1, 1, 1)로 엄격 고정하고, Spline Control Point 거리만을 조절하여 영역을 처리할 수 있도록 함.

- 카메라 시점 거리별 동적 LOD (Level of Detail) 연동  
Cesium Camera Manager 값을 조절함. 카메라의 FOV(시야각)와 이동 속도, 바라보는 방향에 맞춰 화면에 실제로 보이거나 가까운 구역의 타일만 dynamic하게 요청 및 수거하도록 세팅하여 프레임 드랍을 방지할 수 있음.

> LOD (Level of Detail)란: 카메라와의 거리에 따라 타일의 해상도(폴리곤 수 및 텍스처 정밀도)를 차등 적용하여, 가까운 곳은 고화질로 렌더링하고 멀리 있는 곳은 저화질로 처리하거나 메모리로부터 회수하여 프레임 드랍을 줄이는 기법

- 런타임 모드 선택 가능 옵션 제공  
- *실시간 스트리밍 모드*: Dynamic LOD 제어로 시각적 사실성을 유지하며 넓은 구역을 동적으로 불러오는 기능.

### Taxiing 지상 주행 구현

- **구현 방법**:

- **조향 - Absolute 절대 회전 모드 사용**:
- 초기, Attitude Control 제어 모드를 구현 하기 전, 공중 비행 모드에선 Absolute 모드 사용시 Yaw 방향 전환시 회전 방향을 누적하는 기능이 없어 기억을 하지 못하는 단점이 있어 AC모드를 도입함.
이후 Taxiing 지상 주행 과정에선, Pitch와 Roll을 사용할 필요가 없어 조향을 위해 Yaw 회전이 필요했음. 이때, AC모드를 사용하면 센서 조종 제어에 어색하고 일관성없는 조향 방식임을 느낌. (Roll -> 조향)
지상에선 Roll 제어를 막아야 자연스럽다고 판단하였으며, 지상에선 물리적으로 바퀴가 지면을 미는 힘으로 오브젝트의 방향 좌우 전환이 자연스럽게 누적되므로 AC가 아닌 Absolute 모드의 Yaw를 도입함.
따라서 지상 주행에선 Absolute 모드를 사용하고 공중 주행에선 Absolute모드와 AC모드를 선택할 수 있는 구조를 구축하기로 기획함.

### Finite State Machine 구조 구현
- **도입 배경**:  
기존 구현 방식에서는 MPU6050 데이터를 갱신하고 저장한 값을 이용해 Flight Rotation Controller 스크립트 내에서 Absolute 쿼터니안을 만들고 바로 Rotation을 적용함.  
만약, Attitude Control 모드를 사용하고자 한다면 Attitude Rotation Controller 스크립트에 계산된 AC 쿼터니안을 만들고 바로 Rotation에 적용하는 구조였음.  
이때 AC Mode Allow 체크박스를 통해 if-else 문으로 두 비행 타입 모드를 선택할 수 있도록 제어함. 
그러나 오브젝트의 이륙, 착륙을 구현 하려면 지상 주행 방식 또한 필요했고 이 방식과 공중 주행 방식의 전환을 원활히 제어하기 위해선 단순 if-else 사용으로는 구조의 복잡성과 추후 유지 보수, 구조 확장에 어려움이 생길 것이라 판단함.
따라서 유한 상태 머신 FSM 구조를 활용하여 오브젝트의 상태의 진입 시작 명령, 동작 명령, 종료시 명령을 State 머신으로 제어하고 물리 제어 스크립트는 현재 오브젝트의 상태와 상관 없이 해당 물리 법칙만 수행하는 단일 기능 원칙을 지킬 수 있도록 도입함.

- **구현 방법**:  
1. MPU6050 센서의 자이로, 가속도 데이터 갱신 및 저장 과정 까지는 동일함.
2. SensorQuaternionCalculator.cs 추가: Flight Rotation Controller 스크립트와 Attitude Rotation Controller 스크립트의 각각의 Abs, AC 쿼터니안 계산을 한 스크립트에서 실행하도록 통일하여 2개의 출력 쿼터니안 데이터를 생성하게 통합함.
3. 비행기 오브젝트가 가질 수 있는 상태 클래스인 TaxiingState(지상 주행 상태), FlyingState(공중 주행 상태), CalibratingState(보정 상태) 클래스 구조 스크립트를 추가함. (IState 인터페이스 사용)
4. StateMachine.cs 추가: 현재 상태와 직전 상태를 IState로 저장 기억하는 기능과 초기 실행 상태 명령 처리(Initialize), 상태 전환 명령 처리(Change) 메서드, Update와 FixedUpdate 처리를 구현한 상태 머신 클래스 구조 스크립트를 추가함.
5. FlightStateController.cs 추가: 직접적인 비행기 오브젝트 상태 제어 스크립트. 각각의 상태와 State Machine의 인스턴스를 생성하고 초기 실행 State를 직접 결정함. MonoBehaviour를 기반으로 (Taxiing으로 설정) Update, FixedUpdate를 직접 호출함.
6. 현재 구현된 상태는 다음과 같으며, 보정 상태는 FlightStateController.cs에서 호출함. TaxiingState와 FlyingState는 비행 상태에 따라 자동으로 변경시킬 예정.

- TaxiingState(지상 주행 상태): Wheel Collider 활성화, 바퀴 모터 토크 적용, Abs 쿼터니안 참조 및 조향에 적용
- FlyingState(공중 주행 상태): Wheel Collider 비활성화, 오브젝트에 전방 추력 엔진 등을 부여, Abs/AC 모드에 따른 쿼터니안 사용 및 Rotation에 적용
- CalibratingState(보정 상태): 오브젝트에 적용된 물리 법칙을 정지, 초기화 (센서 초기화는 해당 클래스가 아닌 앞 과정에서 다룸)

## 트러블 슈팅
### 바이트 스트림 데이터 패킷과 Concurrent Queue 호환 문제
- **기존**: SerialManager.cs 내 기존 사용하던 멀티 스레드 용 Concurrent Queue를 사용하는 환경에서, 데이터 패킷을 String 대신 바이트 스트림 단위로 데이터 패킷 타입을 변경함.
- **문제점**: 복사본 배열 checkArray을 만들어 패킷의 구조를 확인하기 위해 ToArray나 CopyTo 메서드를 사용할 때 디버깅 시 에러가 발생함.
에러가 발생한 원인은 Update() 메서드 안에서 dataQueue.CopyTo(checkArray, 0)을 호출할 때, dataQueue에 쌓여있는 데이터 개수가 멤버로 캐싱 (미리 선언)한 checkArray의 크기(256)보다 커졌기 때문이었음.
이 방법을 채택한 이유로, ConcurrentQueue는 인덱스로 따로 접근할 수 없는 자료구조의 자체 보안성 문제가 있어 배열 복사본 생성을 선택했음.
그러나, 데이터가 쌓이는 속도가 너무 빨라서 어느 순간 dataQueue.Count가 256 Byte을 넘어가버려서 고정 크기인 checkArray에 통째로 복사하려다 보니 공간이 부족해서 ArgumentException이 발생함.
또한, ToArray도 마찬가지로 같은 에러가 뜸과 동시에 Heap 영역에서 생성하므로 가비지 컬렉터를 일으킬 여지가 있었음.
단순히 복사본 배열 바이트 크기 선언을 늘리는 방법도 추후 해당 데이터 수용 스크립트의 유지 보수 문제가 생길 것이라고 판단함.
- **해결**: 다시 처음 lock 오브젝트 방식을 채택하되, 기존과 다르게 lock 오브젝트와 일반 Queue를 같이 사용함.
lock 오브젝트 제어를 통해 멀티 스레드 환경 내 큐의 데이터 보호 수준 안전을 보장함과 동시에, ConcurrentQueue의 인덱스 접근 불가 문제를 일반 Queue로 사용해서 데이터 패킷을 바이트 단위 인덱스로 접근해 두 장점을 모두 살릴 수 있는 방법을 선택함.
또한, Enumerator 열겨형을 채택하여 큐내 바이트 데이터 요소(Element)를 가르키는 이정표 기능으로 이용해 직접 내부로 참조만 하도록 설계함.
이 방식으로 큐 배열을 굳이 복사하지 않고도 헤더와 사이즈, 트레일러를 안전하게 확인하며 동시에 가비지 컬렉터 문제도 방지하는 좋은 방법이 됨.
이 방식을 사용해서 바이트 단위로 데이터를 받아 String과 Split(",") 방식을 사용한 기존보다 유니티에서 더 빠르게 처리할 수 있게 되었음.
또한 큐 방식을 그대로 사용하여 데이터 유실을 방지도 함께 챙길 수 있게 됨.
(데이터 바이트 패킷 -> int 조립 방식은 BitConverter를 사용함; PC환경에 맞춰 리틀 엔디안(Low -> High)으로 자동 조립(window))

lock 오브젝트 사용 성능 검증
1. Serial 버퍼로 부터 바이트 단위 데이터를 읽어올 때 (Enqueue일 때만 lock 시스템 이용)
2. while문 내 일반 Queue 인덱스를 확인할 때 (Dequeue일 때만 lock 시스템 이용)

* 1번의 경우보다 2번의 while문 처리 속도가 시스템 상 훨씬 빠름. 센서 데이터를 받아오는 속도보다 유니티에서 while로 읽고 Dequeue 처리하는 속도가 훨씬 빨라 데이터 유실이 일어나지 않는다.
시리얼 통신이나 네트워크 환경에서 데이터를 읽어올 때, ReadByte()를 단발성으로 호출하는 방식과 while문을 돌며 버퍼를 통째로 비우는 방식의 속도 차이는 매우 크다.
CPU가 while 루프를 돌며 메모리에서 데이터를 Dequeue하는 속도는 나노 초에서 마이크로 초 단위이며, ReadByte()는 상대적으로 매우 느리게 센서 데이터를 Enqueue하므로 최소 100배에서 1,000배 이상 차이가 남.
즉, 데이터 패킷 유실이 일어나지 않는 구조를 가질 수 있음.

* 멀티 스레드 환경 내 lock 오브젝트를 사용하여도, 1번과 2번의 Enqueue와 Dequeue 내에서만 lock 제어를 사용하므로 프로그램의 성능에 거의 영향을 주지 않는다.
큐(Queue) 자료구조에서 데이터를 넣고(Enqueue) 빼는(Dequeue) 작업의 시간 복잡도는 모두 O(1) (상수 시간)이기 때문이다.

### 하드웨어(MPU6050) 제약에 따른 수평축(Yaw) 드리프트 한계
- **물리적 한계 파악**: 본 프로젝트에 사용된 MPU6050 센서는 6축(가속도 3축, 자이로 3축) 기반으로 지구 자기장을 측정할 수 있는 지자기 센서(Magnetometer)가 누락되어 있다.
MPU6050 센서를 이용한 상보 필터 적용으로 Roll과 Pitch의 기울기는 실시간 세계 기준(중력 방향)으로 완벽히 보정했으나, 수평 방위각(Yaw)은 가속도 기준점을 측정할 수 없었다.
측정할 수 없는 이유는 Yaw 방위각(수평면에서의 회전)으로 어떻게 회전하든 중력 가속도는 항상 수직 아래로 작용하므로, Yaw 회전만으로는 센서의 중력 가속도의 크기나 방향이 변하지 않기 때문임.
이는 수평 방위각(Yaw) 계산할 정보 자체가 가속도계에 없기 때문에 오직 자이로 데이터만을 사용할 수 밖에 없었음. 이로 인해 Yaw는 누적 오차(Drift)가 발생할 수밖에 없는 하드웨어적 한계가 존재함.

### WheelCollider Free Rolling 상태에서 저속 AddForce가 무반응하는 문제
- **기존**:  
삼륜 지상 주행(WheelCollider 3개) 구조에서 바퀴에 토크를 전혀 주지 않고 완전한 Free Rolling 상태를 유지한 채 오브젝트 Rigidbody에 추력(AddForce)만 가해 지상 정지 상태에서 출발을 테스트함.

- **문제점**:  
공중에서는 추력(Thrust) 크기가 작던 크던 정상적으로 전방으로 가속되지만, Wheel Collider가 지면에 접촉해있는 상태에서는 추력을 작게 줄때 오브젝트가 제자리에서 전혀 움직이지 않았음.  
반면 비행기 오브젝트를 지면으로부터 살짝 들어 올려 바퀴 접지가 끊기는 순간 즉시 추력이 정상 반영되어 지상 주행이 이어짐. 고속에서는 문제없으나 저속 추력이 주어질 때 움직이지 않는 문제점을 발견함.  
지상 저속 주행은 이륙과 착륙에 꼭 사용되는 상황 중 하나이기에 문제를 해결하고자 원인을 파악함.

- **원인 파악 과정**:  
원인 파악을 위해 Forward/Sideways Friction Curve Stiffness 조절 (마찰력), Wheel Damping Rate (바퀴 회전 감쇠 능력), Suspension Distance (바퀴 스프링 범위), Physics Solver Iterations 상향 (초당 물리 연산 반복 횟수), 지면 바퀴 파임 확인 등 물리 연산 제어 실험을 진행하였으나 전부 무관함을 확인함.  
또한 Rigidbody의 IsSleeping() 상태는 추력이 있을 때 항상 false였음에도 불구하고 움직이지 않아, 단순 Sleep 문제도 아닌 것 같았음.  
이때, 첫 실행 시 오브젝트의 정지 상태에서 추력을 주지 않았을 때 Ridig Body의 Sleep 모드가 True임을 확인함. 결과적으로 인터넷 서칭을 통해, 이 현상은 Wheel Collider의 모터 토크가 0인 Free Rolling 조건일 때 진입하는 유니티 엔진 내 PhysX Vechicles SDK 내부의 별도 저속/정지 처리 방식으로 추측됨.  
확실한 근본적인 원인은 단정할 수 없지만 유니티의 WheelCollider는 소스가 공개된 자체 구현이 아닌 NVIDIA PhysX의 Vehicles SDK를 내부적으로 감싸서 쓰는 비공개 라이브러리이므로 확인할 방법이 없었음.
하지만 Forward/Sideways Stiffness=0 무효, Solver Iteration 무효, Sleep 무효, 속도 주입 무효, 바닥 접지 해제 시 즉시 해결 확인 등 다양한 시도를 해보았고 가설을 통해 PhysX Vehicle SDK가 오브젝트의 정지 상태를 특별 취급하여 인스펙터 값과 무관하게 내부 저속/정차 로직을 사용한 것으로 추측됨.  
실제로 2015년 Unity 5부터 Unity Issue Tracker에 "WheelCollider가 일정 힘 이하에서는 반응하지 않는다"는 리포트가 있어, 정차 중인 오브젝트가 미끄러지지 않게 한 내부 설계가 원인일 수 도 있다고 추측함.

- **해결**:  
모터 토크를 0으로 주는 현실의 완전한 Free-Rolling 대신, 매 FixedUpdate 주기 마다 세 바퀴에 아주 미세한 모터토크 (0에 수렴하는 임계값)를 주입함.  
그 결과, 지상 위 오브젝트의 Position 영향을 최소화 하면서 미세 토크로 정차/저속 처리 로직 발생을 방지할 수 있었음.
실제로 매우 작은 추력을 줬을 때 미세하게 저속으로 오브젝트를 전방으로 전진시킬 수 있어 문제를 해결함.  
적용 후 Ridigbody의 IsSleeping()이 True로 되지 않음을 확인함.

| :--- | :--- | :--- |
| **0 ~ 1** | **Packet Header** | `0xAA`, `0xBB` (패킷 시작 알림) |
| **2** | **Packet Size (Byte)** | `int8_t` (센서 데이터 총 크기 (Byte)) |

| **7 ~ 8** | Accel Z | `int16_t` (MPU6050 가속도 Z축 Raw Data) |
| **9 ~ 10** | Gyro X | `int16_t` (MPU6050 자이로 X축 Raw Data) |
| **11 ~ 12** | Gyro Y | `int16_t` (MPU6050 자이로 Y축 Raw Data) |
| **13 ~ 14** | Gyro Z | `int16_t` (MPU6050 자이로 Z축 Raw Data) |
| **15 ~ 16** | Button Click Signal | `int16_t` (버튼 클릭 시 `1`, 평상시 `0`) |
| **17 ~ 18** | **Packet Tailer** | `0xCC`, `0xDD` (패킷 끝 알림) |
